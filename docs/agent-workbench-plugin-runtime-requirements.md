# Agent Workbench 插件安装与 Skill 运行上下文需求

状态：待实施需求。本文描述目标行为，不代表 Workbench 已实现。

## 1. 结论与目标

插件是能力的安装单位，可包含多个 Skill。安装应完成必要依赖准备与可用性验证；任务执行时，Workbench 根据实际 Runtime、项目和用户选择解析文件路径，再注入 Skill 与脚本执行环境。

首选“安装时准备环境，运行时绑定任务路径”。安装保留插件来源内容，任务投影可以动态生成。性能不是静态改写与动态注入的主要取舍因素，部署约束和 Runtime 兼容性才是。

用户应获得两个结果：

1. 安装成功的能力在其声明支持的执行环境中可用，首次调用无需模型临时猜测并安装依赖。
2. 同一个 Skill 可以用于不同项目和 Runtime，生成文件位置可配置、可覆盖，并能被 Workbench 正确返回给用户。

## 2. 问题与典型场景

- 安装 Skill 目录后，Python 库或外部工具仍然缺失，实际调用才发现不可用。
- 多个 Skill 属于同一场景，却需要分别安装和处理重复依赖。
- Skill 写死开发者本机路径或默认工作目录，换 Runtime 后无法执行，或把文件写到用户找不到的位置。
- 用户指定报告目录，但提示词、脚本参数和产物收集器使用不同路径。
- 宿主与容器看到的路径不同；本机安装成功不能证明容器内能力可用。

示例：用户在项目 A 运行许可证检查，默认报告进入本次任务的产物目录；在项目 B 运行相同 Skill 时，显式要求报告写入项目的 `reports/`。插件来源内容和依赖版本保持相同，本次任务路径分别解析。

## 3. 与现有 Workbench 模型的关系

实施应接入已有对象和流程，避免建立另一套安装、版本与任务体系：

- Plugin Package 是分发与安装单位；Capability Binding 锁定精确版本或摘要。
- Profile Revision 保存能力引用和非秘密配置，不保存某次执行的绝对路径。
- AgentTask Snapshot 记录本次任务解析后的能力、环境与路径配置。
- Runtime 原生 Skill 文件与目录是可重建投影，插件来源包是不可变资产。
- 凭据与权限继续由既有授权、policy 和 sandbox 管理。

依据：Workbench 的 `docs/product/agent-profile-and-capability-plugin-model.md` 与 `docs/engineering/third-party-component-delivery.md`。实现前需核对这些文档和现有代码的最新状态。

## 4. 安装与依赖准备

### 4.1 安装流程

固定来源与版本 → 校验包结构和摘要 → 检查权限与执行要求 → 准备依赖 → 在目标执行环境验证 → 记录可用状态 → 投影可用能力。

- 插件声明支持的 Runtime、平台、必要依赖及最小验证入口。具体 manifest 字段沿用现有格式，实施时确定。
- 首期支持 Python 依赖及已交付的外部工具。Python 环境优先使用 `.venv`，与目标项目的虚拟环境分开。
- 同一插件版本的多个 Skill 可以共用依赖环境；不同插件版本保持隔离。
- 模型调用脚本时使用解析后的解释器和工具路径；不依赖 Shell 的偶然 PATH，也不默认使用被分析项目的 Python 环境。
- 环境准备必须幂等；失败保留原因，允许显式重试。升级验证失败时，已有可用版本继续可用。
- 可用性记录绑定包摘要、目标平台、Runtime 环境及依赖结果。迁移或环境变化后重新验证，不沿用旧环境的成功状态。
- 包或权限校验失败阻止安装；组件特有的依赖失败按现有局部失败语义处理。受影响组件不可调用，其他独立组件可用，界面明确展示部分可用及原因。

### 4.2 两种交付场景

**平台随发布交付的插件：** CI 准备固定版本、校验和依赖产物，部署及生产任务只消费发布产物，遵守现有第三方组件交付规范。

**用户主动安装的插件：** 通过独立、受控的安装操作准备依赖；按部署策略使用批准来源或内部产物。普通任务调用不承担下载与安装职责。若生产策略暂不支持用户插件安装，则明确提示限制，不绕过交付规范。

### 4.3 首期安全检查

- 校验来源、固定版本、内容摘要和归档结构，拒绝越界解包与资源引用。
- 安装前展示需要的文件、网络、进程和凭据权限；安装不自动获得账号授权。
- 依赖安装可能执行第三方代码，应在受控环境内进行，限制可访问目录和凭据。
- 保存检查与安装结果。静态检查通过不等于插件安全，实际权限由执行器强制实施。

首期不建设通用恶意代码检测平台，也不承诺自动识别所有危险插件。

## 5. 任务路径解析与动态注入

### 5.1 路径语义

| 路径 | 用途与生命周期 |
| --- | --- |
| `skill_dir` | 当前 Skill 的脚本、模板和资源，来源内容只读 |
| `workspace_dir` | 当前任务已授权的项目或输入目录；无项目任务可以缺省 |
| `output_dir` | 本次任务的最终产物目录，可由用户覆盖 |
| 临时与持久数据目录 | 使用现有存储机制；插件确有需求时提供，临时文件与最终产物分开 |

以上名称是 Workbench 内部建议约定，不是各 Runtime 共同支持的行业标准。首期先解决前三项，避免提前扩展大量变量。

### 5.2 输出位置规则

优先级：本次任务用户指定 → 项目默认 → 用户默认 → Workbench 任务默认。

- 保存的默认配置与单次覆盖分开；单次覆盖不修改插件来源或全局设置。
- 相对输出路径在有项目时按 `workspace_dir` 解析；无项目且无法确定基准时要求用户补充明确位置。
- 路径由 Workbench 规范化，并校验执行环境中的实际授权范围、可写性和符号链接目标。
- 解析后创建必要目录；越权、不可写或映射失败时明确失败，不静默换目录。
- 路径配置在任务执行前确定并记录快照。用户主动修改本次任务位置时形成显式变更；普通默认设置变化只影响新任务。
- 重试沿用原任务的目标位置与版本，并重新校验环境和权限；已有同名产物遵循现有文件治理策略。

### 5.3 注入与执行一致性

Workbench 必须把同一份解析结果用于：

1. Skill 加载上下文或任务专用文件投影。
2. 脚本的明确参数、解释器路径及必要环境变量。
3. 产物定位、收集与向用户展示。

脚本支持明确参数时优先传参，例如 `--output-dir`。仅在提示词中写入路径不能替代实际参数和权限控制。秘密不混入普通路径上下文，路径进入命令或模板时使用结构化传参和正确转义。

容器或远端 Runtime 注入的是执行侧可见路径。Workbench 保留宿主／存储与执行路径的映射，向用户返回可访问的产物引用，而不是直接展示无法访问的容器绝对路径。

### 5.4 Runtime 适配与兼容

- 支持原生变量或配置注入的 Runtime 使用原生机制。
- 只支持读取 Skill 文件的 Runtime，生成任务专用投影并替换已声明占位符；原始安装文件保持不变。
- 提示词注入适用于遵循上下文的 Skill，但不能修复脚本内部写死的路径。
- 对无法正确消费路径上下文的旧 Skill，明确提示需要修改或标记不兼容；首期不自动重写任意自然语言和代码中的路径。
- ACP 连接本身不意味着具有路径注入或执行约束能力；每个适配器需验证其真实支持程度。

## 6. 用户交互

- 插件详情展示来源、版本、包含的能力、支持环境及安装状态。
- 安装结果展示可用、部分可用或失败，以及具体组件和原因。
- 用户／项目设置提供默认输出位置；任务创建或对话指令允许单次覆盖。
- 任务详情展示实际输出位置和产物入口；默认任务无需反复询问路径。
- 高级诊断可查看实际解释器、依赖验证和路径映射，普通用户流程只展示必要信息。

## 7. 首期范围与实施顺序

1. 核对已有插件、版本、文件治理、任务快照与 Runtime 投影实现，确定接入点。
2. 选一个包含多个 Skill、具有实际 Python 依赖的测试插件，在一个当前支持的 Runtime 中跑通受控安装与验证。
3. 接入默认输出目录和单次覆盖，将路径同时传给 Skill、脚本及产物收集器。
4. 验证第二个 Runtime 的适配差异，保持插件来源内容不变。

首期不做插件市场、跨插件通用依赖求解、任意语言构建平台或全量旧 Skill 自动迁移。缓存复用在正确性验证后再优化。

## 8. 验收标准

| 场景 | 通过条件 |
| --- | --- |
| 多 Skill 插件安装 | 单次安装准备共享依赖，包含的可用 Skill 均能调用 |
| 有第三方 Python 依赖 | 首次调用成功，模型无需安装依赖，目标项目环境未被修改 |
| 安装失败与重试 | 错误可定位；重试幂等；失败升级不破坏已有版本 |
| 部分组件失败 | 失败组件不可调用，独立可用组件仍可调用，状态明确 |
| 安装安全边界 | 摘要不符、越界归档和未授权执行被阻止并记录原因 |
| 两项目使用同一 Skill | 输入和输出分别解析，插件来源摘要不变 |
| 默认与单次覆盖 | 覆盖按优先级生效，默认配置保持不变，用户能打开最终产物 |
| 容器／远端路径 | 执行侧路径正确，产物返回宿主或存储引用正确 |
| 越权或不可写路径 | 执行前明确失败，未在其他目录偷偷生成产物 |
| 任务重试与环境变化 | 保留任务配置，重新校验实际环境；旧可用性记录不能错误放行 |
| 不同 Runtime | 同一插件在两个适配器下完成同类任务，或明确说明不支持的能力 |

测试分别覆盖确定性的解析／安装逻辑与真实 Runtime 的端到端验证；仅证明提示词含有路径不算通过。

## 10. license-check 的边界

license-check 当前采集脚本仅依赖 Python 标准库，JSON 输出到 stdout。它可以作为路径与产物接入案例，但不能证明第三方依赖安装功能已通过验收，依赖验证需另选实际有依赖的测试插件。

Skill 仓库负责清晰声明运行条件、使用可传参的脚本和可移植的资源引用；Workbench 负责插件安装、环境准备、任务路径、权限和产物交付。

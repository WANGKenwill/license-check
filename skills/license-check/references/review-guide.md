# 判断依据

取证和兼容性判断分开：元数据是许可声明，文件原文是具体证据，两者不一致或许可经过修改时，记录差异并保留待确认。文件名识别只是收集策略，不是许可文本识别引擎。

## 使用与分发

先确认组件如何使用：开发工具、运行依赖、链接的库、独立进程、复制的代码、内嵌数据，以及是否经过修改。再确认交付的是源码、打包代码、可执行文件、容器镜像或网络服务。开发依赖也可能随源码或构建产物分发，应检查实际内容。

独立调用用户安装的工具，与把其二进制一起交付是不同事实。进程边界本身不能证明许可兼容；还需考虑接口、组合方式及对应条款。相同依赖在不同分发方式下可能产生不同义务。

## 声明与义务

- AND 表示组合要求，OR 表示许可选项，WITH 表示带例外；保留原文，核对用户实际选择。双许可不能简单归类成其中一个许可证。
- 包级许可不覆盖包内其他组件。逐项查看 ThirdPartyNotices、bundle 的 *.LICENSE、署名和对应组件信息。
- 区分许可证冲突与声明、署名、修改标记、源码提供等义务遗漏。仅发现 copyleft 不足以认定冲突；宽松许可也不代表没有义务。
- 仅有 copyright 或缺少许可文件不能当作获得授权。文本相似也不等于授权条款完全一致。
- Python Classifier 和旧式 License 字段的精度有限。License-Expression 保留原样，License-File 及 RECORD 指向的文件提供原文证据；元数据缺失时不要猜测。

需要得出具体条款结论时，核对该版本的上游许可文本及官方说明。记录来源、适用条件和推断依据；不得把兼容性矩阵或工具分类当作法律结论。

## 案例校准

Playwright 的包根目录声明和内嵌组件声明需要分别收集：ThirdPartyNotices.txt、bundle.js.LICENSE 不应因包级 Apache-2.0 声明而被忽略。

FFmpeg 作为用户安装的独立进程调用时，需确认调用和组合方式；若发布包包含 FFmpeg，则还需核对该二进制的构建配置、许可证及对应分发义务。仅知道“调用 FFmpeg”或“工程是 MIT”不足以判断完整合规。分发方式未知时，两种情况分别说明并保留待确认。
